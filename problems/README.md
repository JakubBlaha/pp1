# Problem tree

A small web app that shows every problem found in the formalism, what each one affects, and how to solve it.

## Open it

Open `problems/index.html` in a browser (double-click it, or `open problems/index.html`). No server is needed. KaTeX (formulas), marked (Markdown) and Cytoscape (graph) are loaded from a CDN, so formulas and the graph need an internet connection; without one, the text is shown as plain source.

## Views

| View | What it shows |
|---|---|
| EC translation (start page) | the first goal, translating every requirement and test case into the Event Calculus: what blocks it, grouped by concept; what has to be built; an ordered plan of the solutions that remove the blockers; and which requirements each blocker stands in the way of |
| Overview | counts, the root causes, a suggested order for the open solutions, and a matrix of unresolved problems per requirement and category |
| Graph | what affects what: solutions → the problems they solve → the problems those lead to → the requirements they affect, and the goal with the problems that block it. Click a node to see only what is connected to it |
| Problems | all problems as a tree organised by concept, with search and filters |
| Solutions | every proposed, applied or rejected solution, with the problems it solves and what it needs first |
| Requirements | each requirement's original text, its formalisation from `examples.tex`, its test cases, its problems and the solutions that change it |

## Data

Everything is generated by `python3 problems/build.py` into `problems/data.js`. Run it after every change; do not edit `data.js` by hand. The build checks all references and stops with a list of errors if something is wrong. It warns about unresolved problems that have no solution yet.

The build reads:

- `problems/items/*.md`: one file per category, problem, solution or goal (format below);
- `tex-new/examples.tex`: each requirement's text, entities, constraint and notes;
- `req/*.md`: the original requirement texts and the test cases.

## Adding a problem

Create `problems/items/<id>.md`. The file name must be the id.

```markdown
---
id: only-if-gap
title: Events happen when the test fires them, but not only then
parent: stimulus-vs-system
status: open
severity: major
found: 2026-10-05
related: d-signal-write, ec-aggregates
caused-by: test-set-of-traces
ec: blocker
ec-why: EC treats the listed events as the only ones; unless the formalism says the same, counts mean something different after translation.
---
## Summary
One or two sentences.

## Explanation
The idea in one sentence, then a concrete example. Formulas: $\mathit{Val}_\rho(e, t)$ inline, $$...$$ on their own line.

## Proposed fix
What to change.

## Affects
- Req 09: how Req 09 is affected
- Req 10 / TC3: how test case TC3 of Req 10 is affected
- all: for problems that concern every requirement
- none: if no current requirement is affected

## Sources
- `research/findings.md`, "…"
```

| Field | Meaning |
|---|---|
| `parent` | the category, or the problem this one is a part of; this builds the tree |
| `status` | `open` (no agreed fix), `decision` (options known, the team has to choose), `proposed` (a fix is proposed), `resolved` (fixed), `closed` (turned out not to be a problem) |
| `severity` | `major`, `medium` or `minor` |
| `caused-by` | problems this one follows from; these become "leads to" arrows in the graph |
| `related` | other problems worth reading; no direction |
| `ec` | how the problem bears on the translation to the Event Calculus: `blocker` (some requirement or test case cannot be translated until it is decided), `work` (something the translator has to do or be built for), `tooling` (needed to run the translated theories, not to write them) or `none` |
| `ec-why` | one sentence saying why; required for every problem. Inline formulas are allowed |

Section names other than Summary, Affects and Sources are free: use "Fix", "Proposed fix", "Decision needed" or "Resolution" as appropriate.

## Adding a solution

A solution is a concrete change that solves one or more problems.

```markdown
---
id: s-controlled-by
kind: solution
title: Record who controls each entity; operations come only from the test
status: proposed
solves: stimulus-vs-system, only-if-gap
partly-solves: system-boundary
needs: s-test-semantics
alternative-to: s-other-solution
---
## Summary
## Change
## Example
## Affects
- Req 09: what changes for Req 09
```

| Field | Meaning |
|---|---|
| `status` | `proposed`, `decision` (one of several alternatives), `applied` or `rejected` |
| `solves`, `partly-solves` | the problems it fixes completely or in part |
| `needs` | solutions that have to be applied first |
| `alternative-to` | solutions it competes with; choose one |

## Categories

Categories are the top level of the tree: `kind: category`, a `title`, a `short` name for the overview matrix and an `order`.

## The goal

`goal-ec-translation.md` (`kind: goal`) describes the first goal: what the translation produces and when it is reached. The EC translation view and the goal node in the graph are built from it and from the `ec` field of every problem.

## When something changes

- **A new problem is found:** add its file, list every affected requirement and test case, link its causes, say whether and why it is in the way of the EC translation (`ec`, `ec-why`), and add or extend a solution. Then run the build.
- **A problem is fixed:** set its status to `resolved`, the solution's status to `applied`, and add a "Resolution" section saying what changed and where.
- **A problem turns out not to be one:** set its status to `closed` and say why. Do not delete it.
