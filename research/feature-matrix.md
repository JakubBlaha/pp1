# Feature matrix: which existing formalisms cover what we need

Each **row** is a feature our formalism needs, with the requirement or goal that needs it.
Each **column** is an existing formalism or tool.
A cell says briefly **how** that formalism achieves the feature. An **empty cell** means the formalism does not cover it.

The columns are those from `related-formalisms.md`, plus eight added because they target the requirement, test-case and coverage side, where the first scan was thin:

| Added column | What it is |
|---|---|
| UPPAAL (+ TRON, CoVer) | Timed automata with a model checker; TRON tests a system online, CoVer generates tests for a coverage criterion |
| SVA / PSL | SystemVerilog Assertions and the Property Specification Language: assertion languages from hardware verification, with built-in `cover` |
| Simulink Req. Table / Test | MathWorks Requirements Table (requirements as precondition / postcondition rows) and Simulink Test assessments |
| SysML v2 | Requirements as constraints (`assume` / `require`) and verification cases that `verify` them |
| Gherkin (BDD) | Given / When / Then test scenarios in plain English (Cucumber) |
| ETSI TDL | Test Description Language: test scenarios as interactions between a TESTER and an SUT, with time constraints and test objectives |
| TTCN-3 | ETSI test language with ports, `send` / `receive`, timers and verdicts |
| ioco / TorXakis | Model-based testing theory and tool with input and output channels |

How to read the cells:
- "as LTL" / "as MTL": the same construction as in that column.
- "FO over `t`": written directly as a first-order formula that quantifies over time points.
- "(discrete)": works only with discrete time.
- "(informal)": only as free text, with no precise meaning.
- Many cells describe an *encoding* (an extra variable, stream, flag or observer automaton that tracks the information), not a built-in operator.

The last row counts the covered features per column. It counts encodings too, so it says *whether* a feature can be expressed, not how naturally.

## What the table shows

- **The Event Calculus still covers the most (38 of 41).** It misses only the natural-language vocabulary, a coverage criterion and requirement–test traceability. It remains the best translation target (`calculi.md`).
- **SVA / PSL come next (34) and are the closest match to our goal as a whole.** They combine:
  - assertions over traces with history operators (`$past`, goto repetition `[->n]`, cycle windows `##[m:n]`);
  - a built-in `cover` construct for coverage;
  - `assume` vs `assert` for stimuli vs checked behaviour.

  Their limits: discrete clock cycles only, and a hardware vocabulary.
- **The test languages cover what the logics miss:**
  - TTCN-3 (26), ETSI TDL (23) and ioco / TorXakis (23) have test cases, the tester/SUT split, channels and "no response" (quiescence or timeouts);
  - but they are weak on history, counting and aggregates.
- **Simulink Requirements Table / Test (25) is the closest industrial tool chain.** Requirements are table rows, tests are harnesses with assessments, and it measures requirements coverage. It is tied to Simulink models, though.
- **Coverage appears in only six columns:** UFC, SVA / PSL `cover`, UPPAAL CoVer, Simulink requirements coverage, TDL test objectives and SysML v2 verification cases. Only UFC defines coverage of the *conditions* inside a requirement. The others count whether a property, edge or objective was reached at all.
- **Rows covered by few columns:**
  - "Interval relations": Allen, Duration Calculus, SFO and the Event Calculus only.
  - "Value just after": only as a discrete "next step" (`X`, `t+1`, primed variables, `##1`), nothing for continuous time.
  - "Requirement ↔ test traceability": the requirement and test languages only, never the logics.
